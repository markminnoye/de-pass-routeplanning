## Global constraints

- Doelfunctie lexicografisch: `(max_ride_s, sum_ride_s, total_drive_s)`. Rittijd per kind = tijd van zijn stop tot school **inclusief dwell van latere stops, exclusief dwell op de eigen stop** — dezelfde formule als `evaluate_bus` (`ride_s` = school-aankomst minus vertrek van de stop).
- Dwell: `settings.dwell_base_s + settings.dwell_per_student_s * |riders|` (defaults 30 + 10·n). Hergebruik `_dwell` uit `evaluate.py` of dezelfde formule; tests bewijzen gelijkheid met `evaluate(...).ride_times_s()`.
- Reistijden komen uit de **matrix** (GeoClient.matrix / handmatrix), nooit uit `calculateRoute` en nooit uit haversine. `optimize` doet **geen TomTom-call** (`usage.transactions == 0`).
- Een opstapplaats is altijd één stop met al zijn leerlingen; de solver splitst nooit.
- `haversine`-strategie in `ordering.py` blijft bestaan en ongewijzigd. Alleen `ordering: auto` + strategie `matrix` gebruikt de nieuwe solver.
- Plugin-kopie: na elke wijziging in `busroutes/` `uv run python scripts/build_plugin.py` zodat `tests/test_build_plugin.py::test_check_passes_on_this_repo` groen blijft.
- DoD na elke task: `uv run ruff check . && uv run ruff format --check . && uv run pytest` groen.
- Commit op branch `wp3-stdlib-solver`. Geen force-push, geen amend van andermans commits.
- WP2-restpunten (`cells.py` extract, `isinstance` in evaluate, CLI data-dir paden) horen **niet** bij WP3 tenzij ze deze task blokkeren.

## Task 1: Scorefunctie + handmatrix-wereld

TDD. Schrijf eerst tests in `tests/test_optimize.py` (nieuw) en een handmatrix-fixture in `tests/conftest.py`. Kijk ze falen. Implementeer daarna `busroutes/optimize.py` — **alleen score, geen zoektocht**.

### Handmatrix in conftest

Nieuwe fixture-wereld, los van de bestaande 4-leerling haversine-wereld:

- Punten: school `S` + stops `A, B, C, D` (elk 1 leerling; ids `a`,`b`,`c`,`d`). Twee bussen met ruime capaciteit (bv. 10).
- `HandMatrixClient` (GeoClient): `matrix()` en `route()` lezen uit dezelfde in-memory dict `(origin_key, dest_key) → seconden` (`busroutes.tomtom._point_key`). Ontbrekend paar → `KeyError` of een duidelijke fout, geen haversine-fallback. `usage = Usage()` met nullen. `snap_to_street` mag identiteit zijn.
- De matrix is **asymmetrisch** en bewust niet evenredig met afstand, zodat later (task 2) padlengte ≠ max-rittijd. Leg de seconden vast in de fixture, niet “ongeveer”.

Minimale matrix die task 2 nodig heeft (nu al neerzetten, task 1 gebruikt hem om te scoren):

Zet school-start = S. Maak twee volgordes waarvan de padkost (S→…→S) en de max-rit uiteenlopen:

- `S→W` goedkoop, `S→Z` duur; keten `W→X→Y→Z→S` lang, keten `Z→Y→X→W→S` kort.
- Concreet (seconden, overige cellen groot bv. 50_000 zodat ze niet per ongeluk winnen):

  | van\to | S | W | X | Y | Z |
  |---|---|---|---|---|---|
  | S | 0 | **10** | 50000 | 50000 | **5000** |
  | W | **40** | 0 | **400** | 50000 | 50000 |
  | X | 50000 | **30** | 0 | **400** | 50000 |
  | Y | 50000 | 50000 | **30** | 0 | **400** |
  | Z | **40** | 50000 | 50000 | **30** | 0 |

  Voorwaartse keten W→X→Y→Z is duur (400); terugketen Z→Y→X→W is goedkoop (30). Dan:

  - padkost `S-W-X-Y-Z-S` = 10+400+400+400+40 = 1250
  - padkost `S-Z-Y-X-W-S` = 5000+30+30+30+40 = 5130  → routelengte-heuristiek verkiest W-eerst
  - max-rit `W-X-Y-Z-S` = 400+400+400+40 + 3·dwell = 1240+120 = 1360 (dwell 40 bij 1 kind)
  - max-rit `Z-Y-X-W-S` = 30+30+30+40 + 3·dwell = 130+120 = 250  → rittijd-doel verkiest Z-eerst

  Gebruik stop-ids `w`,`x`,`y`,`z` als de letters in de tabel (of `a`–`d` mapped op W–Z). Documenteer de mapping in de fixture.

Als 5×5 te krap is omdat start=school al in de tabel zit: 4 stops is exact wat de spec vraagt.

### Score

In `busroutes/optimize.py`:

- `Score = tuple[int, int, int]`  # (max_ride_s, sum_ride_s, total_drive_s)
- `def score_bus(stops: list[Stop], start: Point, school: Point, travel, settings) -> Score`
  - `travel(a: Point, b: Point) -> int` (seconden)
  - Lege stops → `(0, 0, 0)`
  - `max_ride` / `sum_ride`: per kind (opstapplaats met k leerlingen telt k keer in de som, dezelfde rit)
  - `total_drive` = start→s₁ + s₁→…→sₙ→school (geen dwell; gelijk aan som van de legs, zoals `BusResult.drive_s`)
- `def score_scenario(scenario, buses, school, travel, settings) -> Score` somt component 3 over bussen, max/som van ritten over alle kinderen.

### Tests (minimaal)

- `score_bus` op één bus, given order: `max_ride` en `sum_ride` gelijk aan `evaluate_bus` / `evaluate(...).ride_times_s()` met dezelfde `HandMatrixClient` en `ordering: given`. `total_drive` gelijk aan `BusResult.drive_s`.
- Opstapplaats met 2 leerlingen: som telt twee keer, max één keer die rit.
- Lege bus: (0,0,0).
- `score_scenario` is lexicografisch: een lagere max-rit wint, ook als som of rijtijd hoger is.

## Task 2: Niveau A `--order` (2-opt + or-opt) + matrix-auto in evaluate

TDD in `tests/test_optimize.py`. Uitbreiden van `busroutes/optimize.py`.

### Gedrag

- `def order_stops_for_bus(stops, start, school, travel, settings) -> list[Stop]`
  - Start = de **gegeven** volgorde (geen nearest-neighbour).
  - Herhaal tot geen verbetering: **2-opt** (een segment omkeren) en **or-opt** (een segment van 1, 2 of 3 opeenvolgende stops eruit tillen en ergens anders invoegen).
  - Accepteer een zet iff `score_bus(kandidaat) < score_bus(huidig)` (tuple-vergelijking).
  - Deterministisch: vaste nesteling van loops (i, j, lengte, invoegpositie). Geen RNG.
  - 0 of 1 stop: ongewijzigd terug.
- `def optimize_order(scenario, buses, school, travel, settings) -> Scenario`
  - Per bus `order_stops_for_bus`; verdeling ongewijzigd.
  - Resultaat: zelfde bussen/stops, volgorde per bus verbeterd; `ordering` van scenario én elke bus wordt `"given"` (klaar voor serialisatie in task 5).

### Evaluate-koppeling

In `busroutes/evaluate.py`, `_ordered_stops`:

- `plan.ordering == "given"` of ≤1 stop: ongewijzigd (huidige early-return).
- strategie `haversine`: blijf `order_stops` uit `ordering.py` gebruiken (NN + 2-opt op padkost).
- strategie `matrix`: bouw `travel` uit `client.matrix` (één call, zelfde punten als nu: start + stops + school) en roep `order_stops_for_bus` aan. **Niet** `ordering.order_stops`.

Bestaande test `test_auto_ordering_uses_matrix_and_visits_far_stop_first` moet groen blijven óf — als de nieuwe doelfunctie op die 2-stop-haversinewereld een andere volgorde kiest — de assertion aanpassen naar wat de rittijd-doel voorschrijft, plus een assertion dat `matrix_calls` nog 2 is. `test_haversine_ordering_buys_nothing_from_tomtom` blijft de oude heuristiek (far-first) en mag niet van gedrag veranderen.

### Tests (minimaal)

- Handmatrix, 4 stops op **één** bus, startvolgorde = de padkost-winnaar (`w,x,y,z`). `order_stops_for_bus` eindigt op de rittijd-winnaar (`z,y,x,w` of de lexicografisch beste die 2-opt+or-opt kan bereiken). Assert `score_bus(result) < score_bus(start)` en `score_bus(result)[0]` gelijk aan de bekende max-rit van Z-eerst (250 met dwell 40, zie tabel).
- Zelfde geval: `ordering.order_stops` / padkost-2-opt houdt W-eerst (of in ieder geval een **slechtere** max-rit dan de solver). Dit is “verslaat de routelengte-heuristiek”.
- Twee bussen: `optimize_order` herschikt per bus, verplaatst geen stops tussen bussen.
- Idempotente tweede run: zelfde volgorde.
- `evaluate` met `ordering: auto` + `matrix` op de handmatrix-client gebruikt de nieuwe volgorde (niet padkost).

## Task 3: `pinned` / `pinned_stops` in `load_scenario`

TDD in `tests/test_models.py` (en zo nodig een dump-test). Geen zoektocht.

### Model

- `BusPlan` krijgt `pinned: bool = False`.
- `Scenario` krijgt `pinned_stops: tuple[str, ...] = ()` (of `frozenset` — kies één, frozen/hashable bij voorkeur).
- `load_scenario`:
  - bus-object `"pinned": true` → `BusPlan.pinned is True`. Ontbrekend / false → False. Andere waarden → `ScenarioError`.
  - scenario-veld `"pinned_stops": ["w", "pp-x"]` → die ids. Ontbrekend → leeg. Onbekende stop-id (niet op enige bus in dit scenario) → `ScenarioError` die de id noemt.
  - `"pinned": true` op een bus impliceert niet dat z’n stops in `pinned_stops` moeten staan; dat zijn twee aparte mechanismen.

### Serialisatie

Kleine helper `scenario_to_dict(scenario) -> dict` in `busroutes/models.py` (bestaand scenario-JSON-formaat):

- `"ordering": "given"` als je dat zo doorgeeft (de helper dump’t de huidige velden, hij dwingt geen given af).
- stops: string-id als het een thuisstop is (`not stop.is_pickup_point`); anders het opstapplaats-object (`id`, `lat`, `lon`, `name`, `students`).
- `"pinned": true` alleen als True (niet `false` uitschrijven).
- `"pinned_stops"` alleen als niet-leeg.

Nodig in task 5; nu al testen zodat assign-tests het resultaat kunnen vergelijken.

### Tests (minimaal)

- `pinned: true` op bus1 wordt gelezen; bus2 default False.
- `pinned_stops` met bekende ids.
- onbekende id in `pinned_stops` → `ScenarioError`.
- `pinned: "yes"` → `ScenarioError`.
- `scenario_to_dict` round-trip: load → dump → load, gelijke bus-ids, stop-ids, pinned-vlaggen (punten van thuisstops via students.json).

## Task 4: Niveau B `--assign`

TDD in `tests/test_optimize.py`.

### Gedrag

`def optimize_assign(scenario, buses, school, travel, settings, *, seed: int = 0, max_seconds: float = 30.0) -> Scenario`

1. Start = invoerscenario. Elke bus in `scenario.buses` is beschikbaar, ook met lege `stops`. Bussen die niet in het scenario staan worden niet gebruikt.
2. Local search, RNG = `random.Random(seed)`:
   - Buren: **relocate** (één niet-gepinnde stop naar een andere niet-gepinde bus, beste invoegpositie volgens `score_bus` van die bus, daarna A op de twee geraakte bussen) en **swap** (twee niet-gepinde stops van verschillende niet-gepinde bussen wisselen, daarna A op beide).
   - Capaciteit is **hard**: zet die `len(student_ids) > capacity` zou maken, overslaan.
   - Accepteer bij strikte score-daling van het hele scenario.
   - Vastzitten: perturbatie — willekeurig `k=3` niet-gepinde stops verplaatsen naar willekeurige andere niet-gepinde bussen (capaciteit respecteren; minder dan 3 verplaatsen als er minder kandidaten zijn), daarna A op geraakte bussen. Bewaar het beste. Stop bij `max_seconds` **of** 200 opeenvolgende perturbaties zonder verbetering van het bewaarde beste.
3. Vaste elementen:
   - `BusPlan.pinned is True` → die bus wordt niet aangeraakt (geen relocate/swap/perturbatie in of uit, **en geen** `order_stops_for_bus`).
   - stop-id in `scenario.pinned_stops` → blijft op zijn huidige bus; volgorde op die bus **mag** wijzigen (A draait wel, tenzij de bus zelf pinned is).
   - Opstapplaats verhuist als geheel.
4. Output-scenario: `ordering: "given"` op scenario en elke bus.

Tijdsmeting via `time.monotonic` (injecteerbaar `clock`/`sleep` niet nodig als de test `max_seconds=0` geeft of een hele kleine limiet: dan moet hij vrijwel meteen stoppen en minstens de start of één verbeterde buur teruggeven). Voor de `max_seconds`-test: `max_seconds=0` → geen perturbatie-loop van 200, runtime ruim onder 1 s.

### Tests (minimaal)

- Verkeerd ingedeeld kind: 2 bussen, capaciteit 2, vier stops. Zet `a,b` (dicht bij elkaar / korte rit) uit elkaar op verschillende bussen met een “verkeerde” partner; `optimize_assign` groepeert ze beter (score daalt; het kind dat in de handmatrix duidelijk bij de andere cluster hoort, verhuist). Construeer dit op de **bestaande 4-leerling conftest-wereld** of een verkleinde handmatrix met 2+2; documenteer in de test welke startverdeling fout is en welke verhuizing je verwacht.
- Capaciteit: bus1 capacity 1, bus2 capacity 3; een relocate die bus1 zou overladen wordt nooit het resultaat. Assert per bus `len(student_ids) <= capacity`.
- `pinned: true` op bus1: dezelfde stops in dezelfde volgorde na assign; bus2 mag veranderen.
- `pinned_stops: ["c"]`: `c` blijft op zijn startbus; andere stops mogen verhuizen.
- Zelfde seed, zelfde invoer → byte-identieke `scenario_to_dict` (twee calls).
- Andere seed mag anders zijn (geen harde assert verplicht; optioneel).
- `max_seconds=0`: keert terug zonder te hangen.

## Task 5: CLI `optimize` + output + CHANGELOG + schema

TDD in `tests/test_cli.py` (uitbreiden) en eventueel `tests/test_optimize.py` voor de stdout-samenvatting.

### CLI

Subparser `optimize`:

- positief argument: scenario.json
- **één** van `--order` of `--assign` verplicht (mutually exclusive group, required).
- `--seed` default 0 (alleen relevant voor assign; bij `--order` mag hij genegeerd worden).
- `--max-seconds` default 30.0
- `--out` overschrijft het outputpad.
- `--data` / `--samples`-alias zoals evaluate (deprecatie op stderr).
- Geen TomTom-key: `load_settings(require_key=False)` + `OfflineClient(data_dir / "matrix")`. Travel = cellen. Ontbrekend paar → bestaande `OfflineError` → exit 1 via `main()`.
- Default `--out`: `<ouder-van-invoer>/<scenario.name>-optimized.json` (scenario-`name`, niet de bestandsstem als die afwijkt).

### Gedrag

- `--order` → `optimize_order`; `--assign` → `optimize_assign`.
- Schrijf JSON via `scenario_to_dict`. Zet `description` = origineel + ` · geoptimaliseerd (order|assign, seed N)` (N = de gebruikte seed; bij `--order` ook, dan seed 0 tenzij meegegeven).
- `"ordering": "given"` in de output.
- Stdout: compare-achtige vóór/na op **offline-cijfers**. Minimaal: `max_ride_min`, `avg_ride_min`, `total_drive_min` voor/na, en bij `--assign` welke leerling-ids van bus wisselden (`was busX, nu busY`). Geen TomTom. `usage.transactions == 0`.
- Cijfers vóór/na: `score_*` omzetten naar minuten zoals `evaluate.to_dict` (`round(s/60, 1)`), of een echte `evaluate(..., OfflineClient, ...)` op given order — dan is de tabel identiek aan `compare`. Kies evaluate+OfflineClient als de matrix compleet is; dat hergebruikt `compare_markdown` niet per se, een kleine eigen tabel is oké.
